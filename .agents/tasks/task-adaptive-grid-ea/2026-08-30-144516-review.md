# Adaptive gold grid + bounded-martingale recovery EA (v1)

A preset-driven MT5 Expert Advisor for XAUUSD that seeds a grid basket from classical multi-indicator context (RSI/MACD/ATR/EMA + swing S/R), sizes lots with a bounded martingale progression, and manages the whole basket toward a group take-profit. Risk control is deliberately entry-side only: a SafetyValve blocks *new* orders when margin/drawdown thresholds are crossed but never force-closes and never halts, and the RecoveryEngine's only close path is a profit-gated `CloseBasket()`. An optional ONNX inference hook ships disabled and advisory-only. The build could not be compiled or backtested here (no MetaEditor/MT5/wine), so this is a by-inspection review of the MQL5 source.

Watch for: (1) **confirmed** — points-mode group take-profit uses the weighted-average of a single side, so once a hedge is open the break-even/TP target is computed against the wrong basis and can fire early or never; (2) **confirmed** — hedge and averaging both use total basket position count as the grid level index, so an open hedge inflates the progression exponent and consumes `max_grid_levels`; (3) **possible** — averaging has no throttle between adds beyond the moving weighted-average, so a fast adverse move can stack several levels within one bar. The single most important requirement — never realize a loss, never halt — is honored across every safety and recovery path.

**Verdict**: NEEDS_CHANGES

## High-level view

The safety contract the user insisted on is met. Nowhere in SafetyValve, RecoveryEngine, or OnDeinit is there a loss-realizing close, an `ExpertRemove`, or a position modification; the only close is `CloseBasket()` guarded by `pnl > 0` in both TP modes, and every new-order intent is routed through `SafetyValve.CanOpenNew` before any send. The margin-projection path fails closed (blocks on `OrderCalcMargin` failure).

The bounded-martingale claim also holds. Every lot returned by LotSizer passes through `ApplyBounds` — per-order `max_lot_cap`, then remaining `max_basket_exposure_lots`, then broker `NormalizeLot` — and grid depth is capped by `max_grid_levels`. The five presets are exposed as an enum input and the README table matches `Config.mqh` literals field-for-field.

The grid is genuinely adaptive: spacing is `ATR_points * atr_spacing_multiplier` widened in high-vol and tightened in calm regimes, seed direction comes from EMA trend + blended RSI/MACD momentum, and levels can snap to swing S/R. Classical signals are labelled honestly and the ONNX hook is disabled by default, returns neutral, and can only veto (never create) an entry — it cannot bypass the gate.

The gaps are in the recovery geometry once hedging is involved. The points-mode TP and both the averaging and hedge level indices assume a one-sided basket; with a hedge open they read the wrong break-even and the wrong level count. The averaging trigger also lacks an explicit anti-restack guard, relying on the weighted-average shifting to self-throttle.

<details>
<summary>Issues (5)</summary>

1. **Points-mode TP after a hedge** — `GroupTargetReached` (points mode) computes the target from `WeightedAvgEntry(dominant side)` only, ignoring the opposite hedge leg, so the group-profit price target is wrong whenever both sides are open. Compute break-even across the whole net basket, or restrict points-mode TP to un-hedged baskets. Currency mode is unaffected.
2. **Grid level index counts both sides** — averaging (`RecoveryLot(mc,dir,count)` / `BuildNextLevelIntent(...,count)`) and the hedge path use `CountBasketPositions()` as the level index. An open hedge inflates the martingale exponent and eats into `max_grid_levels`. Track the recovery-side level count separately from total basket count.
3. **No throttle between averaging adds** — averaging fires whenever price is one step adverse of the weighted average, re-evaluated every tick while a basket is open. In a fast adverse move this can stack several levels in one bar before the average catches up. Add an explicit last-add price/level guard or minimum spacing check.
4. **NormalizeLot can slightly exceed exposure cap** — when remaining basket room is between 0 and the broker volume minimum, `ApplyBounds` clamps to `room` then `NormalizeLot` rounds up to `vmin`, returning a lot larger than the intended cap. Return 0 (cannot add) when `room < vmin` instead of normalizing above it.
5. **Seed lot risk model assumes gold contract specifics** — `SeedLot` derives risk from `SYMBOL_TRADE_TICK_VALUE`/`TICK_SIZE`; on some gold feeds these are quoted per-ounce vs per-contract and the ATR-stop notional may not match the intended risk %. Verify against your broker's contract size during backtest. (possible)

### SafetyValve never closes or halts — the core contract holds

`SafetyValve.CanOpenNew` only ever returns an allow/block decision; it reads `ACCOUNT_MARGIN_LEVEL`, `ACCOUNT_MARGIN_FREE`, projected free margin via `OrderCalcMargin`, and tracked-peak drawdown, and on any breach it sets `allowed=false` and returns. There is no `PositionClose`/`OrderClose`/`ExpertRemove` anywhere in the file. The projected-margin branch fails closed — if `OrderCalcMargin` cannot compute, the entry is blocked rather than allowed (confirmed). The margin-level floor is only enforced when `ACCOUNT_MARGIN > 0`, which avoids blocking the first seed on an idle account where margin level reads 0.

RecoveryEngine's only close is `CloseBasket()`, reached exclusively inside the `GroupTargetReached` branch, and both TP modes additionally guard `pnl > 0`. When `CloseBasket()` fails on a transient error it logs and holds for the next tick — it never escalates to a forced close. `OnDeinit` leaves open positions untouched. This is the "hold, never realize a loss, never halt" model the user demanded.

### Bounded martingale — no unbounded path

`LotSizer.ApplyBounds` is the single choke point every returned lot passes through: clamp to `max_lot_cap`, subtract current `BasketVolume()` from `max_basket_exposure_lots` and clamp to the remainder (returning 0 when no room), then `OrderManager.NormalizeLot` for broker min/max/step. `SeedLot` and `RecoveryLot` both end in `ApplyBounds`, and `RecoveryLot` floors the progression factor at 1.0. Grid depth is independently capped: `BuildNextLevelIntent` returns invalid once `current_levels >= max_grid_levels`. The progression is `base_lot * factor^level` with a bounded ±25% momentum nudge applied *before* `ApplyBounds`, so the nudge can never breach a cap.

One boundary leak: `ApplyBounds` clamps `lot` to `room` and then calls `NormalizeLot`, which rounds up to the broker volume minimum if `room` is below it. So when remaining basket room is a fraction of a lot step below `vmin`, the returned lot exceeds `max_basket_exposure_lots` by up to one `vmin`. Prefer returning 0 when `room < vmin` (confirmed, low severity).

### Points-mode group TP is wrong once a hedge exists

```
BasketDirection() -> dominant side by volume
be = WeightedAvgEntry(dir)          // ONE side only
target_price = be +/- tp_points*point
```

In currency mode the target uses `BasketFloatingPnL()`, which sums both legs, so a hedged basket is evaluated correctly. In points mode the break-even is taken from the dominant side's weighted average alone and the opposite hedge leg is invisible to the calculation. Once `EnableHedge` opens a counter-position, the true net break-even is not that single-side average, so the points-mode target fires at the wrong price. The `pnl > 0` guard still prevents a loss close, so this manifests as the TP never triggering, or triggering late/early relative to intent (confirmed). Either compute a net-basket break-even across both sides or disallow points-mode TP while a hedge is open.

### Level index conflates basket count with grid depth

Both the averaging add and the hedge pass `CountBasketPositions()` as the level index:

```
lot = m_lot.RecoveryLot(mc,dir,count);
GridIntent gi = m_grid.BuildNextLevelIntent(mc,dir,avg,count);
```

`count` is every position sharing magic+symbol, including any hedge leg. After a hedge is placed, the next averaging add is sized as `base_lot * factor^(count)` where `count` is inflated by the hedge, jumping the martingale exponent, and `BuildNextLevelIntent`'s `current_levels >= max_grid_levels` check trips sooner because the hedge consumes a slot. On a one-sided basket (the default, hedging off) this is correct; with hedging on it distorts both sizing and depth (confirmed). Track a per-recovery-side level counter rather than the raw basket count.

### Averaging has no explicit anti-restack guard

The averaging trigger is `PriceMovedOneStepAdverse`: price at least one adaptive step beyond the weighted-average entry. OnTick re-evaluates the context every tick while a basket is open and calls `Manage` every tick, and averaging returns immediately after proposing one add. The only thing preventing repeated adds on consecutive ticks is that each fill pulls the weighted average toward price, which usually clears the one-step condition. In a fast, gapping adverse move several ticks can pass with price still a full step beyond the laggingly-updated average, stacking multiple levels within a single bar until an exposure or depth cap stops it. The exposure caps bound the *total* damage, so this is not a blow-up path, but it consumes grid depth faster than the "one level per adverse step" intent implies (possible). A last-added-level price stamp, or gating adds to new bars, would make the spacing deterministic.

### Adaptive analysis and honest labelling

Spacing, direction, and recovery aggression are all condition-driven. `AdaptiveStepPoints` scales ATR by the preset multiplier and then ×1.35 / ×0.75 by volatility regime with a min-step floor; seed direction is EMA-cross-plus-slope with an RSI/MACD momentum tiebreak; recovery lot carries a bounded momentum-alignment nudge. Indicator handles are validated in `Init`, released in `Deinit`, and buffers are read at shift 1 (last closed bar), so the analysis is not reading a forming bar. `MarketContext.ready=false` short-circuits OnTick, so a failed buffer copy holds rather than trades on stale data. Classical signals are never dressed up as ML in MarketAnalysis or MLHook.

### ONNX hook is inert and cannot bypass the gate

`CMLHook` defaults to disabled, and even when enabled it deliberately leaves `m_loaded=false` (Phase-2 tensor plumbing is stubbed with TODO markers), so `Predict` always returns a neutral/inactive result in the shipped build. In OnTick the ML result can only *veto* a classical seed whose direction it disagrees with; it never creates an intent and never reaches a send on its own, and `ExecuteIntentGated` applies the SafetyValve unconditionally afterward. Confidence is explicitly not synthesized from the classical context.

### Defensive order handling and isolation

OrderManager stamps the magic number, filters every basket query by magic+symbol, checks `HasMarginFor` via `OrderCalcMargin` before sending, inspects retcodes, and retries only on a whitelisted set of transient codes with a sleep. `ExecuteIntentGated` adds a second margin check after the SafetyValve. One caveat: `IsTradeContextFree()` returns `!IsStopped()`, which is not the same as MT5's terminal trade-context availability (`TerminalInfoInteger(TERMINAL_TRADE_ALLOWED)` / a busy trade thread); in practice CTrade serializes sends, but the helper name overstates what it checks (possible, low severity).

### README honesty

The README states that the EA was not compiled or backtested in this environment and that compilation (F7) and Strategy Tester backtesting are the user's responsibility, and the RISK WARNING section says in plain language that grid+martingale can blow up via broker stop-out and that "always closes in profit" is a design goal, not a guarantee. The preset table was cross-checked against `Config.mqh` and matches field-for-field.
